# Agent Note: 用户资源授权

Status: proposed

[English](2026-11-18-user-resource-authorization.md) | 中文

## 问题

[按用户 realm 分区](2026-11-18-per-user-realm-partitioning.zh.md) 按人分离持久存储。它不分离按资源 id 为键的注册表：`ctx.sessions` 与 `ctx.agents` 持有每个实时会话，不论谁启动，而 Remote 调用只需一个会话 id 就能到达它。

本应堵住该缺口的策略过滤的是列表，不是入口。`createUserAccessPolicy` 按调用从调用者拥有的会话与工作区 id 计算绑定（[`packages/api/remote-access/src/user-policy.ts`](../../../../packages/api/remote-access/src/user-policy.ts)），控制器用它们过滤返回值。Gateway 对每次调用都问策略，而策略拒绝其不绑定的具名资源的调用。这部分是有效的。

不成立的是绑定所据以计算的归属事实本身。`UserAccessFacts.sessions(key)` 与 `.workspaces(key)` 由宿主提供，而分区自身的文档陈述了当前限制：`sessionQuery` 作用域限定在调用者的持久根，因此实时会话不携带任何归属事实，被排除在作用域列表之外。一个实时但由另一用户创建的会话因此落在每个列表过滤之外，却仍可按 id 到达。

同一处还衍生出两个更窄的缺口：

**归属由位置推导，而非记录。** 会话的 owner 从它的日志位于哪个目录推断。任何在用户根之外写入日志或读取日志的事都会改变被推断的 owner。记录的 owner 是事实；推断的 owner 是存储布局的后果。

**拒绝码混淆了两种失败。** 当请求命名了任何非全局资源时，`explainUserRefusal` 报告 `user/resource-not-owned`，否则报告 `user/no-access`。调用者无法区分"该会话属于别人"与"该会话不存在"，这既是体验缺口，也是枚举预言机：两种响应不同，用户即可探测存在的 id。

## 提案

在创建资源处记录归属，在端点处授权，并让拒绝保持一致。

### 记录 owner

`SessionHeader` 增加一个可选 owner 字段，携带规范用户键。它在会话创建时从已认证 principal 写入一次；对 operator 与进程内创建则缺省，从而让每个既有单用户日志字节不变。

该字段属于头部而非旁表，因为归属在会话整个生命期内不可变，且必须经受目录移动、fork 与复制。fork 继承源会话的 owner。subagent 继承其父的 owner，因为父是启动它的唯一当事方。

这是持久化类型变更，需要仓库对已声明持久化类型所要求的确认，以及会话格式规则下的版本决策：现有读取器拒绝未知头部键（[`packages/session/session-persistence-jsonl/src/format.ts:163`](../../../../packages/session/session-persistence-jsonl/src/format.ts) 要求每个键都在 `HEADER_KEYS` 中），因此该字段的加入对读取器可见，必须连同其读取器行为一起按版本处理，而不能塞进当前版本。

### 授权每个端点，而非只有列表

每个 Session 与 Workspace Remote 端点都通过策略解析其资源，而策略把 `user` principal 恰好绑定到记录 owner 等于调用者键的那些 id。该绑定已存在；变化的是背后的事实，从"日志位于我的目录下"变为"头部记录了我"。

创建资源的端点不接受资源参数，因此由全局角色准入。命名资源的端点除非被策略绑定否则拒绝。既有的 `USER_SESSION_ROLE` 与 `USER_WORKSPACE_ROLE` 动作列表就是已准入集合；新端点必须被分类，而不是默认准入。

### 每次未命中使用同一拒绝

用户请求策略未绑定的资源时，无论该资源属于别人还是不存在，都返回相同的错误码与消息。理由在于抗枚举，而它不牺牲合法调用者需要的东西：出现在某人自己列表中的会话永远是他们能打开的会话。

独立的 `user/no-access` 码保留给没有任何角色列出的端点，因为那是运维要调试的组合故障，而不是用户可见状况。

### 针对分类的门禁

分类正是会腐坏的部分：新增一个 Remote 端点，没人分类，它便按恰好匹配的全局角色静默准入。一项仓库门禁读取 Typert 端点表，要求每个端点出现在三处之一——某个用户角色的动作列表、显式的仅 owner 声明、或显式的拒绝用户声明。未分类的端点让门禁失败。

这遵循仓库关于"可机械检查的不变量应接入已执行门禁"的规则，且是让保证能活过下一个端点的唯一办法。

## 备选方案

**继续从持久路径推导归属。** 它不需格式变更也不需迁移。它同时也看不到实时会话，而那恰是可到达集合；它让归属成为日志写在哪里的函数，而不是谁创建了它的函数。已拒绝：结构上无法回答该问题。

**把实时会话移入按用户注册表。** realm 拥有自己的 `sessions` 与 `agents` 注册表，来自另一个 realm 的 id 就根本解析不出。这是最强的形态，且能把策略从会话路径上完全移除。本次变更不采用它，因为 Agent loop、subagent 工厂与 Gateway 的实时控制流都从同一个存储解析会话，拆分它比它所服务分区的范围更大。若策略表面继续增长，这仍是正确的长期形态。

**默认拒绝并按端点显式授予。** 这是分类门禁趋近的方向，但在运行时应用会破坏每个没有 principal 的进程内调用者。门禁在构建时取得同样的保护，且对策略看不见的调用者无运行时变化。

## 验收标准

- 用户 A 创建的会话在其头部记录 A 的规范键；operator 创建的会话不记录 owner。
- A 的会话的 fork 归 A 所有；A 的会话的 subagent 归 A 所有。
- 用户 B 以 A 的会话 id 调用任何 Session 端点，返回未找到形态的拒绝。
- 用户 B 以不存在的 id 调用，得到字节相同的拒绝。
- 每个已列出的 Session 与 Workspace 端点都在门禁中被分类；新增未分类端点让它失败。
- 不含 owner 字段的既有日志保持可读，并按书面规则解析为 operator 拥有或无主，且新版本的读取器行为在两个方向上都被测试。
- 两套 SDK 的期望输出与录制的会话快照都反映该头部变更。

## 风险

**会话头部的持久化变更是最冒险的部分。** 它触及格式状态文档、读取器兼容性评审、持久化目录以及两套 SDK 投影。该字段可选且不可变，是可得的最廉价形态，但版本上调会让新旧世代共存于磁盘，且迁移故事必须在变更落地前写明。

**无主会话仅对 operator 可达。** 既有会话不携带 owner。把它们解析为 operator 拥有是保守选择——没人获得他们此前没有的访问权——但在此变更之前创建过会话的人在之后无法打开它。按目录位置打 owner 的迁移会重新引入本提案移除的推断，因此它必须是显式的运维操作。

**门禁需要一个本身是生成的真相来源。** Typert 端点表是生成的；分类列表是手写的。重命名端点的生成器变更会以与授权无关的理由让门禁失败，而失败消息必须说明这一点。

**统一拒绝掩盖了真实诊断。** 运维排查用户报告时，若不看服务端日志就无法区分归属未命中与会话缺失。区别存在于日志中，而不在 wire 上。
